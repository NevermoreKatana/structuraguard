# Документация

## Вход

Подтверждённое публичное поведение, целевая аудитория и изменённые contracts/examples.

## Результат

Краткая русская документация с проверяемыми примерами, ограничениями и результатом docs checks.

## Workflow

1. Документируй только подтверждённое поведение текущего кода или утверждённый design.
2. Пиши по-русски; identifiers, команды и API signatures сохраняй без перевода.
3. Начинай с задачи пользователя и минимального рабочего примера.
4. Публичный docstring описывает назначение, параметры, результат, исключения, side effects и security ограничения; не пересказывает тело функции.
5. Комментарий в коде объясняет «почему», invariant или threat control. Удали комментарий, если ясное имя делает его ненужным.
6. Примеры должны быть копируемыми, без реальных secrets и, по возможности, проверяться doctest/example test.
7. При breaking change обнови migration note; при архитектурном решении добавь краткий ADR.
8. Не дублируй полный текст ТЗ в нескольких документах. Ссылайся на канонический раздел.
9. Запусти docs build и проверку ссылок, если настроены.

Используй [стиль документации](references/DOCS_STYLE.md).
