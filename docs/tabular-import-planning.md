# Семантический план табличного импорта

`TabularImportPlanner` составляет проверяемый план перед обычным `ingest`.
Модель видит исходные заголовки, ограниченную выборку реальных строк и все
разрешённые изменяемые колонки одной существующей таблицы. Лексического top-k нет:
`Индекс` со значениями `666333`, `001234` может соответствовать `postal_code`,
даже если имена написаны на разных языках. Одна длина числа не доказывает смысл.

В запрос включены ограниченные `split_candidates`: физически допустимые разбиения
полных значений из той же выборки, параметры операции и пример каждой части.
Разделители берутся из значений, не из заголовков; числовой индекс не становится
составным из-за `_` в названии. Это свидетельства структуры, а не готовые
сопоставления: LLM выбирает перенос/разделение и целевые колонки по смыслу.
Цельные UUID, ISO-даты, время и десятичные значения получают признак `value_kind`,
если вся полная выборка имеет эту форму. Их внутреннюю пунктуацию SDK не предлагает
как `split_candidates`; модель всё ещё может выбрать осмысленное разделение с
полным покрытием частей. Неоднородная или усечённая выборка не получает этот признак.

```python
from decimal import Decimal

from structuraguard.contracts.semantic_mapping import SemanticMappingContext
from structuraguard.mapping.tabular import (
    TabularImportPlanner,
    tabular_import_prompt,
    tabular_import_response_schema,
)
from structuraguard.mapping.tabular_execution import execute_tabular_import

# При создании provider зарегистрируйте отдельные prompt/schema, возвращаемые
# tabular_import_prompt() и tabular_import_response_schema(). Router использует
# LOCAL_ONLY и тот же run_id; scanner — trusted base SecurityScanner.
planner = TabularImportPlanner(
    router=router,
    scanner=scanner,
    context=SemanticMappingContext(run_id=run_id),
    min_confidence=Decimal("0.85"),
)
plan = await planner.plan(labels=labels, rows=rows, catalog=catalog, scope=scope)
prepared = execute_tabular_import(labels, rows, catalog, scope, plan)
# prepared.rows передайте штатному ingest как JSON: проверки MappingPlan,
# типов, ограничений и транзакционная загрузка остаются обязательными.
```

Ответ модели содержит только opaque IDs `s0`/`c0`, уверенность, закрытую причину
и одну из двух операций. `copy` сохраняет значение целиком. `split` делит по
пробельным символам либо указанному буквальному разделителю: например,
`Фамилия_имя` → `family_name` и `given_name`. Число частей и их порядок фиксированы,
все части должны использоваться. SDK проверяет **каждую** строку, включая строки,
которые не попали в выборку. Недостаток частей, лишняя часть, неизвестный target,
повторная запись в колонку или уверенность ниже порога отклоняют весь план.
До публикации плана SDK дополнительно проверяет UUID, DATE и INTEGER через
существующие проверки scalar/normalization. `TABULAR_IMPORT_TARGET_VALUE_INVALID`
содержит номер строки, источник, целевую колонку, ожидаемый canonical type и коды
проверок без исходного значения. Проверочная копия INTEGER не меняет выходные
строки; штатная normalization/DB validation в ingest остаётся обязательной.
Никаких произвольных выражений, исправления ответа или генерации значений нет.

Если для исходного поля нет подходящей целевой колонки, LLM может явно указать
`omissions: [{"source_id": "s2", "reason": "no_target_column", "confidence": 0.98}]`.
Это отдельное решение, не отсутствие сопоставления: каждое поле обязано быть
либо перенесено/разделено, либо явно исключено. Повторный, неизвестный или уже
сопоставленный `source_id` отклоняется; уверенность исключения проверяется тем же
порогом. Неоднозначный смысл требует `ambiguous`, а не исключения поля. Хотя бы
одно поле должно быть перенесено, обязательные целевые колонки остаются обязательными.
`prepared.omissions` содержит исходное имя, причину и уверенность исключения;
`prepared.preview[].omitted` сохраняет исключённые значения рядом с полным `before`.
Приложение должно показывать эти решения пользователю вместе с переносами.
Пустой список по умолчанию сохраняет прежнее поведение и fingerprint плана.
В response schema `2.0.0` модель возвращает отдельное решение для каждого
исходного поля: `source_id`, короткое `explanation` (до 240 символов), затем
`operation: copy|split|omit`, упорядоченные `target_ids`, `split_mode`, `delimiter`
и `confidence`. Корень содержит `decision`, `fields` и `confidence`.
Объяснение помогает модели отделить отвергнутый вариант от выбранного действия;
оно скрыто в repr и не переносится в публичный план или безопасную диагностику.
Сырой ответ локальной LLM остаётся чувствительным.

SDK только разворачивает это явное решение в прежний `TabularImportSuggestion`:
`copy` имеет одну цель, `omit` — ни одной, а у `split` число и индексы частей
определяются полным порядком `target_ids`. Причины публичных операций:
`semantic_equivalence`, `composite_component`, `no_target_column` соответственно.
Смысл и действие выбирает модель. Публичные DTO и сохранённые планы совместимы.

Для 1–16 исходных полей native decoder фиксирует по одному решению на каждое
поле, включая пустое, и разрешает только aliases текущих целевых колонок.
Имена и значения в grammar не включаются. Более широкая таблица и JSON-object
fallback используют общую схему с обязательной проверкой покрытия в binder.
Исходный DTO, projected schema и штатный executor проверяются после ответа;
фактическая grammar имеет отдельный fingerprint в `LLMResponse`.
`min_confidence` передаётся в approved payload; низкий score нельзя повышать
ради прохождения порога. `ambiguous` и `unsupported` не разрешают перенос.

Если модель предложила разделение с неверным числом частей, несогласованные
операции, несовместимое с типом БД значение или покрытие (пропуск источника/обязательной
колонки, коллизия целей), SDK один раз
запрашивает **новый план**: передаёт отклонённый план, координаты проблемной
записи и ожидаемые/фактические параметры проверки. Дополнительные сырые строки не
раскрываются. Это не исправление ответа силами SDK и не повтор прежнего запроса.
Новый запрос заново проходит классификацию, scanner и exact-bound approval;
общие лимиты времени, размера и бюджета сохраняются. Оба вызова видны через
обычные hooks provider/router. Новый план проходит ту же проверку всех строк.
Повторный отказ возвращает исходный код ошибки с `planning_attempts=2` и
`plan_origin=llm`; ошибку плана нельзя выдавать за доказанную ошибку CSV.
Ошибки схемы JSON, недостаточная уверенность, security veto и отмена не запускают
перепланирование. Семантический смысл и решение `copy`/`split` остаются за LLM.

`TabularImportPlan` связан fingerprints с исходными строками, каталогом и областью
разрешённых колонок. `prepared.lineage` показывает исходное поле, целевую колонку,
операцию и уверенность; `prepared.preview` содержит первые три строки до и после.
Эти данные чувствительны: обычные логи не должны включать их сериализацию.

Реальные примеры разрешены только при явном `LOCAL_ONLY` и локальном provider.
Класс данных не ниже `CONFIDENTIAL`, неизвестная metadata сохраняет `RESTRICTED`.
SDK самостоятельно запрещает выявленные secrets и active content, добавляет
injection scan и требует exact-bound approval внешнего scanner. Defaults:
8 равномерно выбранных строк, до 256 символов в ячейке, до 64 исходных/целевых
колонок и 64 KiB payload. Усечение значения явно отмечается в запросе и не
меняет исходные строки. Лимиты router, provider и security scanner действуют
дополнительно; превышение не приводит к скрытому исключению кандидатов.

Первый вариант поддерживает одну целевую таблицу и строковые/NULL ячейки,
до 5000 строк и 8 MiB snapshot. Он не выполняет SQL, не создаёт таблицы,
не выводит произвольные преобразования и не заменяет штатную валидацию загрузки.
