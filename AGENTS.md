# StructuraGuard — постоянные инструкции для Codex

## 1. Язык и стиль общения

- Отвечай пользователю на русском языке.
- Пиши документацию, docstring и содержательные комментарии на русском.
- Идентификаторы, имена файлов, публичные API, коды ошибок и Conventional Commit types оставляй на английском.
- Комментируй только неочевидные причины, ограничения и угрозы. Не пересказывай очевидный код.
- Финальный ответ должен содержать только: результат, изменённые файлы, выполненные проверки и оставшиеся риски.
- Не дублируй большие фрагменты кода и не пересказывай постановку задачи без необходимости.

## 2. Экономия контекста

- Не читай полное ТЗ целиком для каждой задачи.
- Сначала прочитай `docs/codex/PROJECT_CONTEXT.md` и `docs/codex/SPEC_INDEX.md`.
- Затем найди только нужные разделы ТЗ через `rg` либо `python scripts/extract_spec_sections.py`.
- Читай интерфейсы, реализацию и тесты только затронутого модуля. Не обходи весь репозиторий без причины.
- Не перечитывай неизменённые файлы. Не печатай большие файлы полностью, используй диапазоны строк.
- Перед работой выбери применимые навыки из `.agents/skills`; подробные references открывай только при необходимости.

## 3. Источники требований

Приоритет источников:

1. Текущая задача пользователя.
2. `AGENTS.override.md` или ближайший вложенный `AGENTS.md`.
3. Корневой `AGENTS.md`.
4. Утверждённые ADR в `docs/adr/`.
5. `StructuraGuard_SDK_Technical_Specification.md`.
6. Существующее поведение и тесты.

Не меняй смысл требования молча. При обнаружении противоречия зафиксируй принятое решение в итоговом отчёте, а архитектурное решение — в ADR.

## 4. Архитектурные инварианты

- StructuraGuard — встраиваемая Python-библиотека, а не веб-сервис.
- Ядро не зависит от FastAPI, Django, Celery, Redis и UI.
- `domain` не импортирует инфраструктуру.
- Парсеры, БД, LLM, staging, аудит и security подключаются через protocols/adapters.
- Основной API асинхронный; sync API — отдельная оболочка.
- Никаких сетевых запросов, чтения окружения, создания таблиц или изменения logging при импорте пакета.
- Никакого глобального mutable state.
- LLM никогда не генерирует исполняемый SQL и не получает доступ к БД или инструментам.
- DDL запрещён в штатном ingest pipeline.
- Любая загрузка поддерживает `dry_run`, allowlist, staging, транзакцию и rollback.

## 5. Требования к Python-коду

- Python 3.12+, строгая типизация публичного API.
- Предпочитай простое прямое решение. Не создавай абстракцию без реального варианта использования.
- Функция выполняет одну задачу; зависимости явные; побочные эффекты локализованы.
- Используй ранний выход вместо глубокой вложенности.
- Не скрывай ошибки молчаливыми fallback. Возвращай typed exceptions и machine-readable error codes.
- Денежные значения — `Decimal`; время — timezone-aware UTC.
- Не используй необоснованный `Any`, broad `except Exception`, boolean trap arguments и mutable default values.
- Сохраняй обратную совместимость публичного API либо явно документируй breaking change.
- Не добавляй production dependency без необходимости и проверки лицензии, поддержки и рисков supply chain.

## 6. Безопасность

- Любой файл, текст, metadata БД и ответ LLM считай недоверенными.
- Запрещены `eval`, `exec`, `pickle`, unsafe YAML loader, `shell=True`, выполнение макросов, JavaScript, SQL-файлов и вывода модели.
- XML external entities, удалённые DTD и сетевой доступ парсеров запрещены.
- Не логируй secrets, DSN, токены, authorization headers и restricted data.
- SQL только параметризованный и формируется DB adapter.
- Для анализа и записи используй разные DB users.
- Для изменений на trust boundary применяй `$structuraguard-security`.

## 7. Рабочий цикл

1. Зафиксируй наблюдаемое поведение и критерии готовности.
2. Для нетривиальной задачи составь краткий план через `$structuraguard-plan`.
3. Добавь или обнови тест, подтверждающий требование или воспроизводящий дефект.
4. Внеси минимальное связное изменение.
5. Запусти узкие тесты изменённого модуля.
6. Выполни review diff через `$structuraguard-review`.
7. Перед заявлением о готовности запусти актуальные quality gates.

Не отключай тесты, type checks или security checks ради зелёного результата. Не заявляй об успехе без свежего вывода команд.

## 8. Обязательные проверки перед завершением

По мере появления соответствующих targets:

- `make lint`
- `make typecheck`
- `make test`
- `make test-integration`
- `make test-security`
- `make docs`

Во время разработки запускай минимально достаточные тесты; полный набор — перед завершением milestone или merge.
